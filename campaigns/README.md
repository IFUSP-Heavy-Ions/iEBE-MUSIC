# Campaigns

One small directory per simulation campaign that is used in a publication. It
records **which code, which container, which design, which parameters and
which seeds**, in a form compact enough to live in git: nothing here is large,
and nothing is stored that can be regenerated exactly.

| campaign | system | design points | framework revision | image |
|---|---|---|---|---|
| [`zr96-c2`](zr96-c2/) | A = 96 isobars, 200 GeV | 1–1000, 2001–2360 | `17ae5b4` (tag `campaign/zr96-c2`) | `iebe-music_slim_17ae5b4_f5242628.sif`, [doi:10.5281/zenodo.24293947](https://doi.org/10.5281/zenodo.24293947) |

Campaigns run before `zr96-c2` are not recorded: they passed only the energy
density to hydro and are superseded.

## What a record contains

| file | what it is | size |
|---|---|---|
| `campaign.yaml` | the manifest: framework revision, image md5, toolchain and binary hashes, design file and digest of the dictionaries, seed rules, job structure | ~5 kB |
| `components.lock.yaml` | every source revision compiled into the image; generated by `scripts/campaign_lock.py` | ~4 kB |
| the design CSV | one row per design point | < 1 MB |
| `singularity.submit`, `run_singularity.sh` | one submit file and the worker wrapper, as they ran | ~8 kB |
| `NOTES.md`, `priors.md`, `design_notes.md` | the physics configuration, the prior ranges and how the design was derived | text |
| `operations/` | the loops and feeders that drove this campaign on OSG; site-specific, kept as a starting point for the next one | scripts |

Deliberately absent: the parameter dictionaries (regenerated from the design by
`MakeDictionaries.py`; the manifest carries a digest to check them against), the
image (hundreds of MB; archived outside git, identified by md5), and the results.

## How a result is tied to source code

```
image (md5)
  └─ docker/Dockerfile                        base image by digest, pinned Python packages
       └─ framework @ commit                  <- "the revision of the chain"
            └─ codes/get_code_packages.sh     each physics code @ commit         
```

The framework commit therefore fixes every source in the image, and
`components.lock.yaml` spells the list out. Since November 2026 the Dockerfile
also installs system packages from a frozen OS snapshot, so the compiler is
fixed too and a rebuild produces the same binaries. The zr96-c2 image predates
that: its recipe took whatever the repositories served that day. That is why
its manifest records the toolchain versions and the md5 of each built binary —
a rebuild that reproduces those hashes is the same code in every sense — and
why the image file itself is archived as well.

## Reproducing a campaign

```bash
git clone https://github.com/IFUSP-Heavy-Ions/iEBE-MUSIC && cd iEBE-MUSIC

# 1. inputs: regenerate the dictionaries and check the digest in campaign.yaml
python3 MakeDictionaries.py --design campaigns/zr96-c2/design_lhs2360_A96_c2_ext.csv \
    --start-design-point 1 --end-design-point 1000 --output-dir zr96_design_c2

# 2. code: obtain the archived image and check its md5, or rebuild it from the
#    framework revision and compare the binary hashes
#    (image.recipe in campaign.yaml names the Dockerfile; it is the one from the
#    commit *after* the framework revision, because a Dockerfile cannot pin
#    the commit that contains it)
git show 06cc504:docker/Dockerfile | \
    docker build --build-arg WITH_OPTIONAL_CODES=0 -t iebe-music:zr96-c2 -

# 3. one event (TRENTo, free streaming, MUSIC, iSS x3, decays, analysis; ~3 min)
python3 generate_jobs.py -w test -n 1 \
    -par zr96_design_c2/DesignPoint1/parameter_dictionary_design_point_1.py
cd test/event_0 && bash submit_job.script
```

Across machines the initial state and the hydro agree, but sampled particle
tables differ at the 0.1–1 % level because last-bit differences in the hydro
reseed the particle sampler; on one machine a re-run is bit-identical.

## Recording a new campaign

1. Build the image and name it `<name>_<framework-sha>_<md5prefix8>.sif`.
2. `python3 scripts/campaign_lock.py --dockerfile-commit <sha> > campaigns/<name>/components.lock.yaml`
3. Copy `zr96-c2/campaign.yaml`, fill it in, add the design CSV, one submit
   file and the wrapper.
4. Tag the framework revision inside the image `campaign/<name>`.
